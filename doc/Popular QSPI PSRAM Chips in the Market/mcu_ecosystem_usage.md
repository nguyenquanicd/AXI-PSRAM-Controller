# Real-World MCU/IoT Ecosystem Usage of QSPI PSRAM

## Which PSRAM chips (manufacturer + part number) are used on official/reference boards, per platform?

### Takeaway
Espressif's ESP32/ESP32-S2/original ESP32-WROVER modules use discrete PSRAM dice that are either Espressif-branded (ESP-PSRAM32/64/64H) or, in practice, pin/command-compatible third-party parts from AP Memory (APS6404) and IPUS (IPS6404) — all of which share the same de-facto-standard SPI PSRAM opcode set. Newer ESP32-S3 modules integrate the PSRAM die inside the module package (no separate discrete chip on the carrier board) and Espressif does not publish the die's original manufacturer part number. RP2350/Pico boards commonly pair with AP Memory APS6404L. STM32 official discovery kits use AP Memory APS6408L/APS6404L. Silicon Labs SiWx917 and GigaDevice GD32 also document QSPI-PSRAM support, but this research could not confirm the exact default PSRAM part number on their official reference boards. Nordic nRF53/nRF91 QSPI peripherals are hardcoded for NOR flash and do not support external PSRAM at all.

### Cited Findings
- ESP-IDF/Espressif documentation states officially supported/validated PSRAM chips are Espressif-branded parts: **ESP-PSRAM32, ESP-PSRAM64, ESP-PSRAM64H** — [ESP-PSRAM64 & ESP-PSRAM64H Datasheet](https://www.espressif.com/sites/default/files/documentation/esp-psram64_esp-psram64h_datasheet_en.pdf); [ESP-IDF External RAM guide](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/external-ram.html)
- ESP32-WROVER (original) datasheet: module integrates "an additional 64 Mbit SPI PSRAM operating at 1.8V"; ESP32-WROVER-B/IB: "8 MB PSRAM operating at 3.3V, up to 133 MHz" — [ESP32-WROVER Datasheet](https://cdn-shop.adafruit.com/product-files/3384/esp32-wrover_datasheet_en.pdf); [ESP32-WROVER-B/IB Datasheet](https://documentation.espressif.com/esp32-wrover-b_datasheet_en.html)
- Community/forum consensus (ESP32 forum "Supported PSRAM Chips" thread, cross-confirmed via search snippets — direct fetch blocked by a bot-check page so treat as secondary-sourced) reports that **AP Memory APS6404** and **Ipus/IPUS IPS6404** are pin- and command-compatible drop-in alternatives to Espressif's ESP-PSRAM32/64, and that "APS6404L is fully compatible with IPS6404L" — [ESP32 Forum thread](https://esp32.com/viewtopic.php?t=17636) (fetch blocked by bot-check; content summarized from search index)
- ESP32-S3-WROOM-1 modules: "the modules use PSRAM integrated in the chip's package"; variants embed the **ESP32-S3R8** SoC (Octal PSRAM in-package, up to 8 MB) or ESP32-S3R2 (Quad, 2 MB) — no discrete PSRAM chip appears on the module's own external BOM, so no separate manufacturer part number is published for the die — [ESP32-S3-WROOM-1 Datasheet](https://documentation.espressif.com/esp32-s3-wroom-1_wroom-1u_datasheet_en.pdf); [Espressif ESP32-S3 Hardware Design Guidelines — Schematic Checklist](https://docs.espressif.com/projects/esp-hardware-design-guidelines/en/latest/esp32s3/schematic-checklist.html)
- Espressif's own ESP32-S3 hardware design guideline explicitly declines to name approved third-party PSRAM parts in public docs: "To reduce the risk of software compatibility issues, it is recommended to use flash and PSRAM models officially validated by Espressif" and directs integrators to "consult the sales or technical support team" for the validated list — [ESP32-S3 Schematic Checklist](https://docs.espressif.com/projects/esp-hardware-design-guidelines/en/latest/esp32s3/schematic-checklist.html)
- RP2350 (Raspberry Pi Pico 2 family): community/vendor boards add **AP Memory APS6404L(-3SQR)** over the RP2350's QMI (QSPI Memory Interface). Example: Adafruit Feather RP2350 with 8 MB PSRAM; Pimoroni Pico Plus 2/2W include PSRAM — [RP2350 Wikipedia summary of ecosystem](https://en.wikipedia.org/wiki/RP2350); [APS6404L PSRAM on RP2350 — nibble-shift errors thread](https://forums.raspberrypi.com/viewtopic.php?t=392957); [rp2350-psram-test driver source referencing APS6404](https://github.com/Altaflux/rp2350-psram-test/blob/main/src/psram.rs)
- STMicroelectronics **STM32L4P5G-DK** Discovery kit ships with **APMemory APS6408L-3OBx (BGA24, 8 MB)** Octal PSRAM, and the board additionally provides "both QSPI and OPI PSRAM footprint on board" for alternate population — [STM32L4P5G-DK BSP source](https://github.com/STMicroelectronics/stm32l4p5g-dk-bsp/blob/main/stm32l4p5g_discovery_psram.c); [STM32L4P5G-DK product page](https://www.st.com/en/evaluation-tools/stm32l4p5g-dk.html)
- ST community/support explicitly maps Espressif's ESP-PSRAM64H to its industry-standard equivalent for non-Espressif hosts: "the equivalent part is APS6404L-3SQR-SN" and notes ESP-PSRAM64H is "only supporting ESP32" — [ST Community: ESP-PSRAM64H and STM32H743 QSPI mode](https://community.st.com/s/question/0D53W00000NVsy1SAD/esppsram64h-and-stm32h743-qspi-mode)
- ST community threads document real designs pairing **APS6404L-3SQR** with STM32H7B0RBT6 over Octal-SPI/QuadSPI — [STM32H7B0RBT6 with QSPI PSRAM APS6404L-3SQR](https://community.st.com/t5/stm32-mcus-products/stm32h7b0rbt6-with-qspi-psram-aps6404l-3sqr/td-p/596182); [STM32H7B0 OCTA SPI not working for APS6404 QSPI RAM](https://community.st.com/t5/stm32-mcus-products/stm32h7b0-octa-spi-not-working-for-aps6404-qspi-ram/td-p/710009)
- ST's application note **AN5050** is the cited reference for configuring the OCTOSPI peripheral generally (mentioned in ST community answers), and ST recommends STM32L5, STM32L4P5/Q5, STM32H7A3/B3, and STM32H72x/73x for full memory-mapped Quad (APSxx04x) or Octal (APSxx08x) PSRAM support — [ST community thread citing AN5050](https://community.st.com/t5/stm32-mcus-products/esp-psram64h-and-stm32h743-qspi-mode/td-p/205754)
- GigaDevice **GD32F5HC** series: "QSPI and SQPI interfaces support external PSRAM/Flash memory... up to 45 MHz." **GD32G5** series: "one QSPI supporting up to 200 MHz DDR/SDR" plus an EXMC (external memory controller) for SRAM/PSRAM/ROM/NOR — [GigaDevice GD32F5HC launch](https://www.gigadevice.com/about/news-and-event/news/gigadevice-launches-gd32f5hc-mcu); [GigaDevice GD32G5 launch](https://www.gigadevice.com/about/news-and-event/news/gigadevice-launches-the-gd32g5-series-mcus). No official reference-board BOM naming a specific PSRAM part number was found for either GD32 line in this pass.
- Bouffalo Lab: PSRAM support via an AXI-bus-attached controller is documented as **"PSRAM (Only for BL618)"**, i.e., the BL616 variant itself does not support PSRAM while its sibling BL618 does; BL602 documentation only discusses QSPI/SPI NOR flash (with OTFAD), not PSRAM — [BL616/BL618 Datasheet v2.5](https://aithinker-static.oss-cn-shenzhen.aliyuncs.com/docs/_media_old/bl616_bl618_ds_en_2.5_open_.pdf); [CNX Software BL616/BL618 overview](https://www.cnx-software.com/2022/12/29/bouffalo-lab-bl616-bl618-risc-v-mcu-wifi-6-bluetooth-5-2-zigbee/). No specific reference-board PSRAM part number was found for BL618.
- Silicon Labs **SiWx917** (Wi-Fi SoC) documents external PSRAM connected "through the quad serial peripheral interface (QSPI) controller," supporting memory-mapped auto-mode reads/writes, per the official PSRAM Developer Guide and application note AN1494 — [SiWx917 PSRAM Developer Guide](https://docs.silabs.com/wifi-developer-guides/latest/external-memory-psram/); [AN1494: SiWx917 External Flash and PSRAM Application Note](https://www.silabs.com/documents/public/application-notes/an1494-siwx917_external_flash-psram.pdf) (PDF could not be text-extracted in this pass; the specific supported part number(s) remain unconfirmed — see Gaps)
- Nordic **nRF5340**: the QSPI peripheral is "tailored around a specific set of NOR flash chips with hard coded commands," and Nordic DevZone engineers describe external RAM support as unsupported/unclear: "doesn't support external RAM, only external flash" — [nRF5340 QSPI and external PSRAM — Nordic DevZone Q&A](https://devzone.nordicsemi.com/f/nordic-q-a/104403/nrf5340-qspi-and-external-psram); [nRF5340 External XIP configuration docs](https://docs.nordicsemi.com/bundle/ncs-2.9.2/page/nrf/app_dev/device_guides/nrf53/qspi_xip_guide_nrf5340.html)

### Inferences
- The embedded industry has converged on AP Memory's (and historically ISSI/Lyontek's) SPI/QPI PSRAM command set as a de facto standard; Espressif-branded, AP Memory, and IPUS PSRAM parts are treated as interchangeable at the command level for Quad-mode designs, which is why third-party PSRAM "just works" on many ESP32/RP2350/STM32 boards despite vendors only formally validating their own or one partner's part number.
- For newer, higher-density SoCs (ESP32-S3 Octal PSRAM, STM32 Octal/DTR designs), the trend is toward tighter SoC/PSRAM co-design (in-package die for ESP32-S3, DQS-based DTR framing) which reduces cross-vendor interchangeability compared to classic single-data-rate Quad PSRAM.

### Gaps
- Could not confirm the original silicon manufacturer of the PSRAM die integrated inside ESP32-S3-WROOM-1/2 (Espressif does not publish this in public datasheets or the hardware design guideline; it directs inquiries to "sales or technical support team").
- Could not confirm a specific official reference-board PSRAM part number for Bouffalo Lab BL618, GigaDevice GD32F5HC/GD32G5, or Silicon Labs SiWx917 boards — searches found controller-level support claims but not BOM-level part numbers within the tool budget for this pass.
- The ESP32 forum "Supported PSRAM Chips" thread (a commonly cited community source) could not be directly fetched (bot-check page blocked automated retrieval); findings from it above are based on the search engine's indexed summary, not primary-source text, and should be treated as lower-confidence pending manual verification.

## What command opcode set and dummy-cycle configuration does each SoC's PSRAM controller/driver actually implement? Hardcoded vs configurable?

### Takeaway
Espressif's ESP-IDF hardcodes one fixed opcode set per PSRAM line-mode family (a "Quad" set shared by ESP32/ESP32-S2/ESP32-S3-Quad, and a separate "Octal DTR" set for ESP32-S3-Octal/ESP32-P4), with dummy-cycle *base* values also hardcoded as C constants — though ESP32/S2/S3-Quad add a small software-adjustable "extra dummy cycle" on top of the fixed base to compensate for board/frequency timing. The RP2350 QMI hardware block, by contrast, exposes read/write opcode, prefix-length, and dummy-length as directly configurable memory-mapped registers, which firmware sets to the specific values needed for its chosen PSRAM part (typically 0xEB/0x38 with 24-bit dummy-length field, i.e. 6 PSRAM clock cycles in quad width) — making RP2350 the more "generic configurable controller" of the two ecosystems documented here.

### Cited Findings
- **ESP32 / ESP32-S2 (Quad PSRAM)** — from ESP-IDF source `components/esp_psram/esp32/esp_psram_impl_quad.c`, opcodes are `#define` constants: `PSRAM_READ 0x03`, `PSRAM_FAST_READ 0x0B`, `PSRAM_FAST_READ_QUAD 0xEB`, `PSRAM_WRITE 0x02`, `PSRAM_QUAD_WRITE 0x38`, `PSRAM_ENTER_QMODE 0x35`, `PSRAM_EXIT_QMODE 0xF5`, `PSRAM_RESET_EN 0x66`, `PSRAM_RESET 0x99`, `PSRAM_SET_BURST_LEN 0xC0`, `PSRAM_DEVICE_ID 0x9F` — [esp_psram_impl_quad.c](https://github.com/espressif/esp-idf/blob/master/components/esp_psram/esp32/esp_psram_impl_quad.c)
- Same file: dummy-cycle base constants are hardcoded — `PSRAM_FAST_READ_DUMMY 0x3` and `PSRAM_FAST_READ_QUAD_DUMMY 0x5` — but the driver also carries a separate `extra_dummy` variable, described in-source as "set based on hardware design" and adjusted at GPIO/frequency configuration time depending on operating clock, meaning the *effective* dummy count is base-plus-tunable-extra rather than a single immutable number — [esp_psram_impl_quad.c](https://github.com/espressif/esp-idf/blob/master/components/esp_psram/esp32/esp_psram_impl_quad.c)
- **ESP32-S3 Octal PSRAM (DTR)** — from `components/esp_psram/esp32s3/esp_psram_impl_octal.c`, opcodes use 16-bit DTR-repeated encodings: `OPI_PSRAM_SYNC_READ 0x0000`, `OPI_PSRAM_SYNC_WRITE 0x8080`, `OPI_PSRAM_REG_READ 0x4040`, `OPI_PSRAM_REG_WRITE 0xC0C0`; command bit-length fixed at 16 bits, address fixed at 32 bits — [esp_psram_impl_octal.c](https://github.com/espressif/esp-idf/blob/master/components/esp_psram/esp32s3/esp_psram_impl_octal.c)
- Same file: dummy-cycle bit-lengths are fixed compile-time constants — `OCT_PSRAM_RD_DUMMY_BITLEN (2*(10-1))` = 18 bits, `OCT_PSRAM_RD_REG_DUMMY_BITLEN (2*(5-1))` = 8 bits, `OCT_PSRAM_WR_DUMMY_BITLEN (2*(5-1))` = 8 bits — described as "not configurable at runtime" in this driver — [esp_psram_impl_octal.c](https://github.com/espressif/esp-idf/blob/master/components/esp_psram/esp32s3/esp_psram_impl_octal.c)
- Espressif's own programming guide confirms mode is a fixed hardware/firmware pairing, not freely mixable: "Quad PSRAM only supports STR mode" and "Octal PSRAM only supports DTR mode," selected via `CONFIG_SPIRAM_MODE` in menuconfig, with flash and PSRAM sharing one internal clock (constraining valid frequency combinations, tabulated for F8R8/F4R8/F4R4 hardware) — [ESP-IDF SPI Flash & PSRAM Config — ESP32-S3](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/flash_psram_config.html)
- ESP32-S3 directory listing on GitHub confirms only one Octal-mode implementation file exists (`esp_psram_impl_octal.c`) alongside `Kconfig.spiram`, i.e. Espressif ships exactly one hardcoded opcode/timing table per line-mode per chip generation rather than a generalized, chip-agnostic opcode table — [esp-idf esp_psram/esp32s3 directory](https://github.com/espressif/esp-idf/tree/master/components/esp_psram/esp32s3)
- ESP-IDF's PSRAM ID/compatibility validation is a hardcoded allow-list, not opcode-flexible: a GitHub issue reports failure on a non-Espressif chip even though menuconfig lists generic options, because `components/esp_hw_support/port/esp32s3/spiram_psram.c` contains `PSRAM_IS_VALID()` macros "specifically written to support the ESP-PSRAM modules and no other modules," producing `PSRAM ID read error` on unrecognized ID bytes — [External non-Espressif PSRAM support — esp-idf#8863](https://github.com/espressif/esp-idf/issues/8863)
- **RP2350 QMI (QSPI Memory Interface)** — a working PSRAM driver's register configuration for the APS6404 shows opcode fields set in firmware, not fixed in silicon: read command register (`m1_rcmd`) set to `0xEB`, write command register (`m1_wcmd`) set to `0x38`, with an initial direct-mode transmit of `0x35` to switch the chip from SPI into QPI at boot. Bus-width fields (`m1_rfmt`/`m1_wfmt`) for prefix/address/suffix/dummy/data are each independently set to "quad," prefix length set to 8 bits, and dummy length set to 24 (bit-field units, corresponding to 6 PSRAM-clock dummy cycles in quad-width transfers) — [rp2350-psram-test driver source](https://github.com/Altaflux/rp2350-psram-test/blob/main/src/psram.rs)
- Community expert guidance on the correct RP2350/APS6404L dummy-cycle count states unambiguously: "it's strictly 6 for read and 0 for write," warning against ad hoc experimentation with other values — [APS6404L PSRAM on RP2350 — nibble-shift errors thread](https://forums.raspberrypi.com/viewtopic.php?t=392957)

### Inferences
- Espressif's PSRAM drivers are best modeled as "hardcoded opcode set with a small firmware-tunable timing fudge factor," not a general-purpose configurable QSPI memory controller — a host emulating ESP32/S3 compatibility would need to match Espressif's exact fixed opcode/dummy tables per line mode rather than expose a fully generic opcode register.
- RP2350's QMI is architecturally closer to "generic configurable QSPI/OSPI memory controller with software-defined opcode, width, and dummy-length fields," which is the shape a broadly-compatible host PSRAM controller should imitate.

### Gaps
- Could not locate/verify the exact opcode and dummy-cycle constants for ESP32-S2's dedicated implementation file (ESP32-S2 appears to reuse the same `esp32/esp_psram_impl_quad.c` given the shared PSRAM_IS_VALID architecture, but this could not be independently confirmed by inspecting an ESP32-S2-specific source path in this pass).
- Did not verify equivalent driver source for ESP32-C-series or ESP32-P4 Hex/Octal PSRAM (`esp_psram_impl_ap_hex.c` / `_ap_oct.c` were referenced only in a search snippet, not fetched and confirmed).
- Could not extract Silicon Labs SiWx917's or GigaDevice's opcode/dummy-cycle configurability from primary documentation (PDF text extraction failed; HTML developer guide page fetched did not contain the register-level detail, which apparently lives in deeper sub-pages not retrieved in this pass).

## Do any of these SoC PSRAM controllers support switching between SPI and QPI/QSPI mode at runtime, and how?

### Takeaway
Yes — both the Espressif ESP32/ESP32-S2 Quad-PSRAM driver and the RP2350 QMI-based driver explicitly issue a software command sequence to switch the attached PSRAM chip from its SPI power-on default into QPI mode, using the same industry-standard opcodes (Enter-QPI = 0x35, Exit-QPI = 0xF5) that also appear in AP Memory's APS6404L datasheet.

### Cited Findings
- ESP-IDF's `esp_psram_impl_quad.c` defines an explicit mode enum `psram_cmd_mode_t { PSRAM_CMD_QPI, PSRAM_CMD_SPI }` and issues `PSRAM_ENTER_QMODE (0x35)` to switch the chip into QPI and `PSRAM_EXIT_QMODE (0xF5)` to "set back to SPI mode" — a real, driver-level SPI↔QPI mode-switch command sequence — [esp_psram_impl_quad.c](https://github.com/espressif/esp-idf/blob/master/components/esp_psram/esp32/esp_psram_impl_quad.c)
- A related ESP-IDF documentation/forum note states "the psram only has QPI mode, so a WP pin setting is necessary on ESP32" — indicating that in practice the classic ESP32 PSRAM path enters QPI once at boot and stays there operationally, using SPI-mode only transiently during the enter sequence (per search-indexed summary; primary source not independently re-verified beyond the search snippet) — (search-index summary, primary page not captured verbatim in this pass)
- RP2350: the community driver sends `0x35` via a direct-mode transmit specifically to move the APS6404 PSRAM chip "from SPI to QPI mode" during initialization, after which all QMI-driven reads/writes use quad-width phases — [rp2350-psram-test driver source](https://github.com/Altaflux/rp2350-psram-test/blob/main/src/psram.rs)
- AP Memory's APS6404L datasheet (per search-indexed excerpts) documents the same pair of commands generically: "Command 0x35 switches the device into quad IO mode and command 0xF5 switches the device back into serial IO mode (only available in QPI mode)," and the device "powers up into SPI mode by default but can also be switched into QPI mode" — [APS6404L-SQH Datasheet](https://www.apmemory.com/en/downloadFiles/0324112120r9601773); [APS6404L-SQN Datasheet](https://www.apmemory.com/tw/downloadFiles/0324112120g3605268)

### Inferences
- 0x35/0xF5 functions as a de facto industry-standard SPI↔QPI toggle for this whole class of PSRAM parts (Espressif ESP-PSRAM, AP Memory APS6404x, IPUS IPS6404x all appear to honor it), so a generic host controller that issues this exact pair at the right point in its init sequence should interoperate with essentially all Quad-mode QSPI PSRAM parts surveyed here.
- The Octal/DTR PSRAM path on ESP32-S3 appears architecturally different (register read/write opcodes rather than an explicit SPI/QPI toggle sequence), suggesting Octal PSRAM parts are typically strapped/negotiated into DTR-Octal mode through a different mechanism than the classic Quad 0x35/0xF5 pair — this could not be fully confirmed from the fetched Octal driver excerpt and is flagged as a gap.

### Gaps
- Could not confirm whether ESP32-S3's Octal PSRAM driver ever issues an explicit "enter Octal DDR mode" command analogous to 0x35, or whether Octal mode entry is instead handled by boot-strapping/register writes only (the fetched excerpt of `esp_psram_impl_octal.c` showed only SYNC_READ/WRITE and REG_READ/WRITE opcodes, no explicit mode-enter opcode).
- Could not verify runtime SPI↔QPI switching behavior for STM32 OCTOSPI/QUADSPI, GigaDevice GD32, Bouffalo Lab, or Silicon Labs SiWx917 controllers from primary documentation in this pass (STM32 forum threads discussed memory-mapped mode limitations but not an explicit mode-switch command sequence).

## Do these controllers support 1-byte vs 2-byte opcodes, configurable dummy-cycle counts, and wrap-burst-boundary toggling? What's configurable vs. fixed in silicon?

### Takeaway
Across the documented ESP-IDF drivers, opcode width, dummy-cycle base value, and command set are fixed per line-mode in firmware source (effectively "fixed in software, not exposed to the end user/registers"), with only a small extra-dummy timing trim exposed for Quad mode; RP2350's QMI hardware, in contrast, genuinely exposes opcode, prefix-length, dummy-length, and per-phase bus width as runtime-programmable registers. A wrap-burst-boundary toggle opcode (0xC0) is part of the standard Quad PSRAM command set (used by both Espressif's driver as `PSRAM_SET_BURST_LEN` and by AP Memory's datasheet as the documented "WRAP_BOUNDARY_TOGGLE" command), but was not observed in the ESP32-S3 Octal PSRAM driver excerpt retrieved.

### Cited Findings
- ESP32/S2 Quad driver: 1-byte opcodes throughout (`0x03`, `0x0B`, `0xEB`, `0x02`, `0x38`, `0x35`, `0xF5`, `0x66`, `0x99`, `0xC0`, `0x9F`), all `#define` constants baked into the C source, not exposed as user-configurable fields — [esp_psram_impl_quad.c](https://github.com/espressif/esp-idf/blob/master/components/esp_psram/esp32/esp_psram_impl_quad.c)
- ESP32-S3 Octal driver: 2-byte (16-bit) opcodes (`0x0000`, `0x8080`, `0x4040`, `0xC0C0`), also fixed constants; command/address bit-lengths (16-bit cmd, 32-bit addr) are likewise fixed `#define`s, not registers a user sets per-chip — [esp_psram_impl_octal.c](https://github.com/espressif/esp-idf/blob/master/components/esp_psram/esp32s3/esp_psram_impl_octal.c)
- The Quad driver's `PSRAM_SET_BURST_LEN (0xC0)` opcode is the wrap/burst-length toggle command, present in the fixed opcode table — [esp_psram_impl_quad.c](https://github.com/espressif/esp-idf/blob/master/components/esp_psram/esp32/esp_psram_impl_quad.c)
- AP Memory's APS6404L command set (per search-indexed datasheet excerpts) independently documents the same function: "The WRAP_BOUNDARY_TOGGLE command is 0xC0" — matching Espressif's constant exactly — [APS6404L Datasheets, multiple revisions](https://www.apmemory.com/tw/downloadFiles/0324112120g3605268)
- RP2350 QMI: opcode registers (`m1_rcmd`, `m1_wcmd`), prefix length (8 bits), dummy length (24, quad-width units), and per-phase bus widths (prefix/address/suffix/dummy/data, each independently selectable as single/dual/quad) are all runtime-programmable memory-mapped fields set by firmware for the specific attached chip, not fixed in RP2350 silicon to one part — [rp2350-psram-test driver source](https://github.com/Altaflux/rp2350-psram-test/blob/main/src/psram.rs)
- Real-world sensitivity of the dummy-cycle field is confirmed by a community post insisting only "6 for read and 0 for write" is correct for APS6404L on RP2350, implying the configurable field must be set precisely to the chip's datasheet requirement rather than left generic — [APS6404L PSRAM on RP2350 — nibble-shift errors thread](https://forums.raspberrypi.com/viewtopic.php?t=392957)

### Inferences
- "Configurable dummy cycles" and "configurable opcodes" are a meaningful differentiator between host designs: Espressif's approach only works because it hardcodes to the specific, narrow de facto standard opcode set that compatible PSRAM parts must implement; a genuinely generic/configurable host controller (opcode + dummy-cycle count both software-settable, as RP2350's QMI is) is inherently more tolerant of PSRAM parts that deviate slightly (e.g., different dummy-cycle requirement at a given frequency, or a non-default opcode).
- The 0xC0 wrap-boundary-toggle command's presence in both Espressif's and AP Memory's independently-documented opcode tables is good evidence this is a genuine cross-vendor standard opcode within the Quad-PSRAM command set, not an Espressif-specific quirk.

### Gaps
- Could not confirm whether ESP32-S3's Octal-mode PSRAM parts (typically in-package, co-designed with Espressif) support or need a wrap-boundary toggle at all — the fetched driver excerpt showed no such opcode, which may mean Octal PSRAM defaults to a fixed wrap/linear-burst behavior not exposed at the opcode layer, but this is inferred, not confirmed from a datasheet.
- Could not verify 1-byte-vs-2-byte opcode configurability or wrap-toggle support for STM32 OCTOSPI/QUADSPI, GD32, Bouffalo Lab, or Silicon Labs controllers from primary documentation within this research pass.

## Known interoperability issues / errata where a specific PSRAM part or revision required special controller handling

### Takeaway
Documented public issues fall into three categories: (1) Espressif's own driver deliberately refuses non-Espressif-branded PSRAM IDs even when pin/command-compatible, causing "PSRAM ID read error" failures that are a software allow-list issue rather than an electrical incompatibility; (2) a confirmed silicon errata on ESP32-C5 involving PSRAM interaction with sleep/reset and with AES/SHA DMA alignment, fixed in ESP-IDF software without a new chip revision; (3) STM32 OCTOSPI/QUADSPI + APS6404/APS6408 interoperability problems that are mostly memory-mapped-write and DQS/errata limitations of the STM32 side, not the PSRAM chip. A widely-discussed RP2350 "nibble-shift" corruption issue with APS6404L, initially suspected to be a controller/timing bug, was root-caused to PCB signal-integrity (trace length, impedance, grounding) rather than a QMI configuration defect once correct dummy-cycle values were used.

### Cited Findings
- **ESP32-S3 "PSRAM ID read error"**: a user with an off-package discrete Quad PSRAM chip on a custom ESP32-S3 board could not initialize PSRAM despite menuconfig allowing the option; error: `PSRAM ID read error: 0x00000000, PSRAM chip not found or not supported, or wrong PSRAM line mode` / `Failed to init external RAM!` — root cause and chip identity not disclosed in the visible issue thread — [esp-idf issue #15653](https://github.com/espressif/esp-idf/issues/15653)
- **ESP-IDF non-Espressif PSRAM rejection**: a separate, more explicit issue traces the same class of failure to source: `components/esp_hw_support/port/esp32s3/spiram_psram.c` contains `PSRAM_IS_VALID()` macros "specifically written to support the ESP-PSRAM modules and no other modules," so a chip returning ID bytes `0x0016709d` (non-Espressif) is rejected with `PSRAM ID read error: 0x0016709d` even though it may be otherwise electrically/command compatible — [esp-idf issue #8863, "External non-Espressif PSRAM support"](https://github.com/espressif/esp-idf/issues/8863)
- **ESP32-C5 PSRAM errata (confirmed, dated)**: Espressif's own bug advisory for ESP-IDF v5.5.1 on ESP32-C5 documents (a) a "PSRAM Reset Hang" where CPU/digital reset operations may hang when PSRAM is enabled, potentially triggering RTC watchdog resets, and (b) "PSRAM data may be corrupted when AES or SHA hardware accesses buffers that are not aligned to a 16-byte boundary." Espressif states fixes exist in ESP-IDF v5.5.2/v6.0/v6.1 (and specific backport commits to v5.5) "without requiring a new silicon revision" — [CNX Software: ESP32-C5 bug advisory](https://www.cnx-software.com/2026/02/28/esp32-c5-bug-advisory-identifies-and-fixes-psram-and-sleep-coexistence-issues/)
- **STM32H743 + ESP-PSRAM64H**: AP Memory's own field engineer, answering on ST's community forum, states the STM32H743's QUADSPI is a "NOR memory Controller" that "doesn't support Memory Mapped Write function," so ESP-PSRAM64H cannot be used with transparent memory-mapped writes on that specific STM32 part; the vendor recommends the equivalent industry part **APS6404L-3SQR-SN** and points to newer STM32 families (H7A3/B3, H72x/73x, L5, L4P5/Q5) for full memory-mapped Quad/Octal PSRAM support — [ST Community: ESP-PSRAM64H and STM32H743 QSPI mode](https://community.st.com/s/question/0D53W00000NVsy1SAD/esppsram64h-and-stm32h743-qspi-mode)
- **STM32H7A3/B3 errata**: a documented ST errata item states "Memory-mapped write error response when DQS output is disabled," requiring DQS to be enabled for memory-mapped writes "even if the memory does not support DQS" — a controller-side silicon errata affecting OCTOSPI PSRAM interoperability, independent of which PSRAM chip is attached — [search-indexed summary of STM32 community/errata discussion](https://community.st.com/t5/stm32-mcus-products/stm32h7b0-octa-spi-not-working-for-aps6404-qspi-ram/td-p/710009)
- **RP2350 + APS6404L "nibble-shift" corruption**: initially appeared to be a controller/dummy-cycle configuration bug, but was root-caused by the community to physical PCB layout — the PSRAM chip was routed with ~14 mm to flash and an additional ~17 mm via-routed trace to PSRAM, with pattern-sensitive corruption (e.g. `0xF0F0F0F0` failed, `0x12345678` passed) consistent with signal integrity rather than firmware. The proper fix required moving the chip closer, impedance-matched traces, a separate ground plane, improved decoupling, and tuned drive strength (~8 mA); a firmware expert in the same thread separately clarified the correct dummy-cycle setting is fixed at "6 for read and 0 for write," warning against ad hoc deviation — [APS6404L PSRAM on RP2350 — nibble-shift errors thread](https://forums.raspberrypi.com/viewtopic.php?t=392957)
- Related RP2350 discussion of a similar-sounding but distinct problem: "RP2350 PSRAM (APS6404L) intermittent boot failure when overclocked, stress tests all pass once booted" — reported as an overclocking-related boot-timing issue rather than a steady-state data-corruption bug — [arduino-pico discussion #3431](https://github.com/earlephilhower/arduino-pico/discussions/3431)

### Inferences
- Most "interoperability" failures documented publicly for Espressif parts are software policy decisions (an ID allow-list) rather than protocol/electrical incompatibility — meaning a generic PSRAM chip that speaks the standard 0x03/0x0B/0xEB/0x02/0x38/0x35/0xF5/0xC0/0x9F command set would very plausibly work electrically with ESP32/S2's Quad driver if the ID check were bypassed/extended, which is exactly the kind of constraint a broadly-compatible host controller should design around (configurable ID validation, or none).
- On the RP2350 side, the most publicized "PSRAM bug" reports in this research turned out to be signal-integrity/PCB issues rather than QMI controller defects — a caution against over-attributing field reports to controller/firmware root causes without verifying PCB layout first.
